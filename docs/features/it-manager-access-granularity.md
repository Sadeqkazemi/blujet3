# فاز دسترسی‌های ریز پنل مدیر IT

## دامنه

این فاز فقط بخش «کاربران و دسترسی‌ها → افزودن کاربر» را تکمیل می‌کند. کاتالوگ
دسترسی‌ها بر اساس واحد سازمانی (بازرگانی، فروش، مالی و IT) از API واقعی
خوانده می‌شود و انتخاب‌های کاربر در جدول `employee_permissions` ثبت می‌شود.
هیچ دادهٔ کسب‌وکاری یا مجوز نمایشیِ بدون پشتوانه اضافه نمی‌شود.

## چک‌لیست پذیرش

- [x] API `GET /it/permissions` کاتالوگ را به تفکیک واحد و بخش برمی‌گرداند.
- [x] واحد فروش به‌صورت سازگار با مدل فعلی، کاتالوگ عملیاتی واحد بازرگانی را
      دریافت می‌کند.
- [x] بازرگانی: آژانس‌های همکار/درخواست همکاری/بدهکاران، مسیرهای پروازی،
      تعریف هواپیما، زیرعملیات پرواز، عملیات، خدمات، گزارش مسافران، قوانین
      باشگاه مشتریان و وب‌سرویس‌ها به گزینه‌های جداگانه تقسیم شده‌اند.
- [x] مالی: آژانس‌ها، اعتبار و تسویه، گزارش‌ها و خروجی و استرداد بلیط گزینه‌های
      جداگانه دارند.
- [x] IT: فهرست و ایجاد کاربر، مدیریت دسترسی، وضعیت حساب، بازنشانی رمز،
      سرویس‌ها، امنیت و خروجی لاگ‌ها ریز شده‌اند.
- [x] کلیدهای قدیمی مانند `fl_manage`، `sv_control` و `us_manage` حفظ شده‌اند
      تا حساب‌های فعلی و guardهای موجود نشکنند.
- [x] وابستگی‌های انتخاب در فرانت و بک‌اند یکسان‌اند؛ مثلاً «مدیریت مسیر»
      پیش‌نیاز مشاهده مسیر را هم انتخاب می‌کند.
- [x] migration افزونه، کاتالوگ را برای پایگاه‌داده‌های موجود به‌صورت
      idempotent درج/به‌روزرسانی می‌کند؛ seed برای نصب تازه از همان catalog
      استفاده می‌کند.
- [x] نگاشت مجوزهای عملیاتی IT به endpointها و guardهای جزئی انجام شد:
      عملیات کاربران (`us_*`)، مشاهده/پیکربندی سرویس‌ها (`sv_view`,
      `sv_control`, `sv_config`)، سیاست و نشست‌های امنیتی (`sc_view`,
      `sc_manage`, `sc_sessions`) و لاگ (`lg_view`) اکنون روی handlerها با
      `@RequiresPermission` مشخص هستند. مجوزهای سطح‌بخش قدیمی (`us_manage`,
      `sv_control`, `sc_manage`) فقط به‌عنوان bundle سازگار با حساب‌های قبلی
      پذیرفته می‌شوند و انتخاب یک مجوز ریز، مجوز گسترده‌تر ایجاد نمی‌کند.
- [x] endpointهای خواندنی گزارش سرویس و SMS نیز با `sv_view` محافظت شده‌اند؛
      mutationهای سرویس با `sv_control`/`sv_config` و mutationهای امنیتی با
      `sc_manage`/`sc_sessions` محافظت می‌شوند.
- [x] مسیرهای عملیاتی واحدهای بازرگانی و مالی نیز به کلیدهای جزئی متصل شدند:
      مسیر/هواپیما/پرواز/عملیات/خدمات/وب‌سرویس/باشگاه/گزارش فروش و اعتبار/
      گزارش مالی/خروجی گزارش. این نگاشت روی handler واقعی اعمال شده است، نه
      فقط روی ناوبری فرانت.
- [x] مجوزهای جدید اطلاعات/فروش پرواز (`fl_sales_view`, `fl_site_sales`,
      `fl_agency_sales`, `fl_agency_allotments`) و داشبورد/تراکنش/تسویه مالی
      (`fn_dashboard`, `fn_transactions`, `fn_settlements`) در انتخاب فرانت،
      ناوبری کارمند و گارد API هم‌تراز شدند.
- [x] کلید مشترک `sv_view` بر اساس واحد سازمانی مسیردهی می‌شود: بازرگانی به
      «خدمات پرواز» و IT به «سرویس‌های سایت». این جداسازی علاوه بر ناوبری، در
      `EmployeePermissionGuard` نیز با `dept` اعمال می‌شود.
- [x] قفل صندلی برای `IT_MANAGER` عمداً خارج از کاتالوگ عملیاتی است و همچنان
      طبق سیاست رزرو فقط برای مدیرعامل، رئیس هیئت‌مدیره، مدیر ارشد و بازرگانی
      مجاز می‌ماند.
- [ ] merge، push و deploy (پس از تکمیل فاز دوم و تأیید کاربر).

## نکتهٔ فنی

انتخاب یک checkbox فقط همان عملیات و پیش‌نیاز خواندنی آن را ثبت می‌کند.
مجوزهای قدیمی سطح‌بخش در guard به‌عنوان bundle سازگار پذیرفته می‌شوند.
